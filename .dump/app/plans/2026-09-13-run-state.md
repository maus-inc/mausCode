# Run state design record

Roadmap step 07, issue #9. This file is the design contract the code follows.
States, transitions, owners and the replay contract are normative. The store
implementation lives in `src/main/lib/runs/run-state.ts`, the shared vocabulary
in `src/shared/run-state.ts`.

## Outcome

Run progress is a row in the database, owned by the main process. A window
reload, a crash, or a second window reads the same truth. The renderer
streaming store is a projection of the run feed, not the source of truth.

## States

`runs.status` is one of six values, declared once in `src/shared/run-state.ts`.

| status | meaning |
| --- | --- |
| `running` | a live owner is streaming this turn |
| `waiting_approval` | the turn is blocked on a user approval answer |
| `completed` | the turn finished and emitted `finish` |
| `error` | the turn failed, an error chunk or throw is the evidence |
| `cancelled` | the user or a superseding send stopped the turn |
| `interrupted` | the app restarted while the run was active, recovered at startup |

Rejected alternative. The Jules port plan
(`.dump/app/plans/2026-09-12-jules-port-plan.md` lines 216 to 218) names a
richer union: `queued`, `starting`, `backgrounded`, `stale`. `queued` belongs
to step 08, which moves the queue into main. `backgrounded` belongs to the
backgrounding work that owns `wake_requested` and `background_progress`
mapping. `stale` and `interrupted` name the same fact, and this step ships
first, so `interrupted` is the spelling every later step cites. The extra
states are additive rows in the same column when their steps land.

## Transitions and owners

Every write to `runs` happens in one transaction with the matching
`run_events` append. The store rejects an illegal transition by ignoring it,
because a late callback from a dead turn must not corrupt a settled row.

| from | to | owner |
| --- | --- | --- |
| (new) | `running` | `startRun`, called by `claude.chat` and `runtime.chat` at send |
| `running` | `waiting_approval` | the chunk observer on `ask-user-question` |
| `waiting_approval` | `running` | `claude.respondToolApproval`, `runtime.respondApproval` |
| `running`, `waiting_approval` | `completed` | `settle` after a `finish` chunk |
| `running`, `waiting_approval` | `error` | `settle` after an `error` chunk or a throw |
| `running`, `waiting_approval` | `cancelled` | the cancel mutations, an unsubscribe, or a superseding send |
| `running`, `waiting_approval` | `interrupted` | startup recovery, and `settle` on an unexplained exit (stop reason `unknown_exit`) |

Terminal states are terminal. `settle` is idempotent. `startRun` settles any
leftover active run for the same sub-chat as `cancelled` with stop reason
`superseded` before it inserts the new row, so one sub-chat has at most one
active run.

## Events

`run_events` is append only, with a unique `(run_id, seq)` index and a
per-run sequence that starts at 1. `runs.last_seq` mirrors the newest seq so
a consumer can compare cursors without touching `run_events`.

| kind | written when | payload |
| --- | --- | --- |
| `created` | `startRun` | engine, mode, model, provider |
| `started` | first chunk observed | empty |
| `approval_requested` | `ask-user-question` observed | tool name, capped |
| `approval_resolved` | approval answered | approved boolean |
| `settled` | every terminal write | stopReason, error text capped at 500 chars, and for recovery the last prior event kind and seq |

Event payloads carry state facts, not transcripts. The full activity log is
triage row 16 and stays deferred, per the step's out-of-scope section.

## Replay and the feed contract

tRPC surface in `src/main/lib/trpc/routers/runs.ts`.

- `runs.get({ runId, afterSeq? })` returns the run row plus every event with
  `seq > afterSeq`. This is the cursor replay a reload uses.
- `runs.list({ subChatId?, activeOnly?, limit? })` returns run rows, newest
  first.
- `runs.subscribe({ subChatId?, afterSeq?, runId? })` is a tRPC subscription.
  On open it replays, then goes live. With `subChatId`, `afterSeq` and the
  `runId` that produced the cursor it replays that run's events past the
  cursor; a cursor from an older run falls back to a snapshot of the newest
  run, because seq is per-run and an old cursor would swallow the new run's
  early events. With `subChatId` and no cursor it emits one snapshot item for
  the newest run. With neither, it emits one snapshot item per active run,
  then live items for every run. A live item is `{ run, event }`. The store
  registers the listener before it reads the replay snapshot, and drops any
  buffered event whose seq the replay already covered, so nothing duplicates
  and nothing drops.

## Recovery

On startup, after `migrate()`, `recoverInterruptedRuns` moves every active
run to `interrupted`. The `settled` event it appends carries the last prior
event's kind and seq as evidence. At startup no turn can have a live owner,
so no liveness probe is needed.

## Wipe and export registration

`src/main/lib/db/wipe.ts` owns the delete order for the chat tree:
`run_events`, `runs`, `sub_chats`, `chats`, then `projects` for the full
wipe. `debug.clearChats` and `debug.clearAllData` call it. The test seeds
every table the live schema declares, runs the wipe, and asserts every table
that references the chat tree is empty by walking the live schema's foreign
keys. No copied table list.

## Renderer projection

`src/renderer/features/agents/stores/run-feed-projection.ts` opens one
`runs.subscribe({})` per window. It maps run status onto the existing
streaming status store: `running` and `waiting_approval` become `streaming`,
`error` becomes `error`, and `completed`, `cancelled` and `interrupted`
become `ready`. It keeps the last seq it applied per run and drops anything
older, so replays and double subscriptions cannot move a status backwards.
The owning window's `useChat` still writes its own optimistic status for the
AI SDK's UI machinery. The feed corrects it, and is the only source after a
reload or in a second window.

## Queue wakeups (superseded 2026-09-17)

`queue-processor.tsx` dropped the 7000 ms inter-message delay to a 500 ms
debounce and the 2000 ms safety poll to a 30000 ms last-resort wakeup. The
reason both shrink: the ready transition now arrives from a run the main
process settled inside the same transaction that persisted the message, and
the projection writes it into the store the queue already subscribes to.
`claude.ts` defers the `finish` chunk until after the message is saved, so a
ready status cannot precede the persisted message.

Step 08 shipped: the queue rows live in main, and `queue-processor.tsx` with
both timers is deleted, so nothing in this section is live code. What
replaced it, and why a timer is no longer needed, is in
`.dump/app/plans/2026-09-17-queue-in-main.md`, which also records what the
safety interval was load bearing for. This section stays as the step 07
record of the numbers it shipped with.

## Engines wired, engines declared absent

The recorder is wired into the two chat engines that own persistent turn
streams: `claude.chat` (legacy Claude Agent SDK) and `runtime.chat` (native
daemon). The remaining provider routers (`codex`, `gemini`, `qwen`, `cline`,
`cursor`, `grok`, `openclaw`, `openrouter`, `roo`, `opencode`, `hermes`)
stream through per-provider copies of the same observable shape. Wiring them
is a six-line change each against the same recorder, filed as a follow-up so
this high-risk step stays reviewable. Their runs are absent from the table
until then, and this record declares that absence per the cross-backend
parity constraint.

## Test strategy

CI installs with `--ignore-scripts`, so better-sqlite3 has no native binding
in the test environment. `src/main/lib/db/test-sqlite.ts` adapts Node 22's
built-in `node:sqlite` to drizzle's better-sqlite3 session surface, giving
the tests a real SQLite database, real generated migrations and real
transactions. The upgrade test applies migrations 0000 through 0014, seeds
rows, then applies the full set, and asserts the old rows survive and the
interrupted case recovers. A fresh-database-only test is not accepted as
proof, per FULL-REVIEW section 16.
